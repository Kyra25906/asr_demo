# 语音实验助手输出与展示策略

首次定义：2026-08-06；最后复核：2026-08-12

> 本文件只定义稳定的输出职责和展示政策。任务状态与实施顺序以
> `PROJECT_TASK_CHECKLIST.md` 为准；当前接线仍主要在 `main.py`，尚未完成
> PresentationCoordinator 集成。

依据真实会话：`20260806_203255`

## 1. 当前问题

当前多个模块直接 `print()`，导致四类信息混在同一终端：

1. 用户真正需要听到的对话；
2. 屏幕上用于确认识别结果的信息；
3. 开发调试和性能指标；
4. 最终需要进入实验记录的数据。

会话 `20260806_203255` 中，用户回答第1段确认后，程序先展示第2段的新追问，
再展示第1段确认成功。这违反“当前回答优先得到反馈”的对话顺序。

确认答复占用了内部口述编号3，下一条实验事件显示为“第4段”，也容易让用户误以为
第3段实验记录丢失。内部口述编号和用户看到的实验步骤编号必须分开。

## 2. 四层输出

### A. VOICE：允许 TTS 朗读

只包含用户下一步必须知道或必须回答的信息：

- 唤醒反馈：“我在，请说。”
- 关键追问：“第1步的样品体积是否为500微升？”
- 确认结果：“已确认第1步。”
- 高优先级异常提醒。
- 会话收尾选择：“还有2项待确认，现在继续吗？”
- 简短结束总结。

默认不朗读“已记录”以及每段完整识别文本，避免打断实验。

### B. SCREEN：展示给用户但不朗读

- 当前用户原始识别文本；
- 与原文不同的规范化候选；
- 简短处理状态：已记录、降级保存、等待确认；
- 当前问题的来源实验步骤；
- 会话结束时的步骤数、异常数、待确认数；
- 用户主动展开时显示的详细结构化内容。

### C. DEBUG：只进入开发日志

- `idle -> listening` 等状态转换；
- 音频文件完整路径；
- FunASR 进度条和 RTF；
- LLM model、token usage、缓存命中；
- LLM 尝试次数、处理耗时；
- 后台队列长度；
- Python 异常堆栈。

默认用户模式不显示；开发模式可通过终端或日志文件查看。

### D. RECORD：领域记录，不是消息渠道

- 原始 ASR、音频路径和识别耗时；
- normalized_text；
- 操作、测量、观察、异常和实体；
- missing_fields 和 confirmation_reason；
- 确认答复与修正内容；
- LLM 尝试次数和耗时；
- 阶段总结与会话总结。

RECORD 数据不等于都要展示，更不等于都要朗读。记录由 storage 层直接持久化，
不再把 `RECORD` 作为 `PresentationMessage` 的输出渠道。

## 2.1 记录、消息与输出形式

### 一条领域记录应定义的特性

领域记录是可追溯事实，至少需要：唯一 ID、session_id、记录类型、创建时间、原始来源、
原始文本或数值、模型整理结果、来源 segment_id、确认状态、版本/修订信息和处理元数据。
不同记录类型可以增加自己的字段，但不得用展示文字代替事实字段。

当前或后续主要记录类型包括：

| 记录 | 保存的事实 | 典型去向 |
|---|---|---|
| ASR 记录 | 原始识别文本、音频、耗时 | JSONL、会话聚合、导出原文 |
| ExperimentEvent | 操作/观察/测量/异常、实体、normalized_text | 实验步骤时间线、总结、导出 |
| PendingClarification | 问题来源、缺失字段、状态、稳定编号 | 当前问题区、待确认列表、会话收尾 |
| ConfirmationRecord | 用户原始答复、目标问题、解决结果 | 审计、确认历史、导出 |
| SessionSummary | 步骤、观察、异常、遗留问题 | 总结区、TTS简版、Markdown/JSON |

### 一条展示消息应定义的特性

展示消息是一次交互行为，不是事实来源。它需要定义：message_id、消息语义 kind、文本、
priority、允许渠道、屏幕语义区域、TTS策略、消息状态、来源 segment/question、是否需要回答、
是否允许暂缓，以及可组合消息组。消息可以过期或取消，但不会因此删除其来源记录。

### 输出形式

| 输出形式 | 消费对象 | 说明 |
|---|---|---|
| JSONL/数据库 | 领域记录 | 核心事实来源，优先保存 |
| 屏幕对话区 | PresentationMessage/DIALOGUE | 用户口述、确认回执等对话 |
| 当前问题区 | PresentationMessage/CURRENT_QUESTION | 当前希望用户回答的一个问题 |
| 实验步骤时间线 | ExperimentEvent/SessionRecord | 长期可见的结构化记录，不靠消息重建 |
| 状态区 | PresentationMessage/STATUS | 已记录、处理中、降级等短状态 |
| 警告区 | PresentationMessage/ALERT | 系统故障或以后经过规则确认的风险 |
| 总结区 | PresentationMessage/SUMMARY + SessionSummary | 屏幕简版与可展开详情 |
| TTS | 可朗读的 PresentationMessage | 只读协调器选出的短消息组 |
| Markdown/JSON导出 | SessionRecord | 不读取终端输出或TTS历史来生成报告 |
| 开发日志 | DEBUG消息和技术日志 | 不进入普通用户界面和TTS |

### 记录与消息的匹配关系

一条记录可以生成零条或多条消息。例如 ASR 记录一定保存，但普通“已记录”可以静默；
一个待确认项可以先后生成首次追问、暂缓回执、回看提示和解决回执。反过来，一条消息也可
引用多条记录，例如会话总结消息来源于多个实验事件。

匹配规则由业务适配器完成：它读取记录和状态，生成 PresentationMessage；
PresentationCoordinator 只负责排序和交付，不能修改原始记录。导出器直接读取 SessionRecord，
不能根据曾经显示或朗读过的消息反推实验事实。

## 3. 一个安全间隙的处理顺序

主线程拿到当前 ASR 后，必须先判断当前输入，再处理较旧的后台消息：

```text
1. 显示当前用户原始识别文本（SCREEN）
2. 判断当前输入类型
   a. 结束指令
   b. 对旧问题的确认答复
   c. 普通实验口述
3. 如果是确认答复：先保存并生成确认回执
4. 收集后台已完成结果，只更新业务状态和消息队列
5. 根据语音预算选择一个短消息组，而不是机械限制为一条
6. 典型消息组是“当前答复回执 + 最多一个相关问题”
7. SCREEN 展示；未来由 TTS 朗读其中允许播放的消息
8. 其余问题保持有效，可暂缓、指定回答或稍后查看
```

禁止后台线程直接打印用户对话或调用 TTS。

## 4. 用户消息优先级

从高到低：

| 优先级 | 消息 | 示例 |
|---:|---|---|
| 1 | 当前答复的直接回执 | “已确认第1步。” |
| 2 | 安全或异常警告 | “发现黑色沉淀，与预期不符。” |
| 3 | ASR 错词确认 | “第1步是否为移液枪和500微升？” |
| 4 | 当前实验缺少的关键参数 | “第2步离心多长时间？” |
| 5 | 普通操作确认 | “已记录。”，默认仅屏幕显示或静默 |
| 6 | 性能和调试信息 | 不进入用户消息队列 |

同一个安全间隙默认最多输出两条、总计不超过50个汉字，并且最多包含一个问题。
这不是硬编码的界面限制，而是第一版语音认知负担预算。

允许的典型组合是“已确认第1步。第2步的离心时间是多少？”。多个历史问题
不能连续朗读，没有直接关系的旧问题应保留到待确认列表。

### 待确认项的调度状态

待确认项将在后续轮次扩展为 `ACTIVE`、`DEFERRED`、`RESOLVED` 和 `EXPIRED`。
“跳过”不等于删除。新问题出现后，优先处理当前操作直接产生的问题和用户明确指定的
问题；已到提醒时机的暂缓问题随后处理，其他历史问题只显示在待确认列表。

用户将可以说“这个先跳过”“查看待确认问题”“回答问题2”。暂缓问题的编号必须稳定，
不能因为新问题加入而重新编号。会话结束时统一提示仍有多少项未解决。

## 5. 编号规则

需要区分：

- `utterance_id`：每次非结束语音的内部编号，确认答复也占号；
- `experiment_step_number`：只对实验事件连续编号，面向用户展示；
- `source_segment_id`：存储中追溯原始 ASR 的内部编号。

例如：

```text
utterance 1 → 实验步骤1
utterance 2 → 实验步骤2
utterance 3 → 对步骤1的确认答复
utterance 4 → 实验步骤3
```

用户界面应显示“实验步骤3”，不能显示“第4段实验步骤”。内部文件仍保留 utterance 4。

## 6. 建议的用户界面输出

### 普通实验口述

```text
你：将样品放入离心机。
状态：已记录实验步骤2。
```

默认不 TTS 朗读“已记录”。

### 产生追问

```text
你：将样品放入离心机。
小科：实验步骤2需要离心多长时间？
```

追问允许 TTS。

### 回答确认

```text
你：是的，是移液枪和500微升。
小科：已确认实验步骤1。
```

必须先给当前回答回执。其他新问题进入下一安全间隙。

### 后台降级

```text
你：加入80毫升去离子水。
状态：原始记录已保存，结构化处理暂时不可用。
```

默认只屏幕展示，不朗读长错误信息。

### 会话结束

```text
小科：实验记录已停止。还有1项待确认，是否现在处理？
```

详细 LLM 耗时、文件路径和 token 信息不展示给普通用户。

## 7. 接入 TTS 的文本规则

- 每条语音尽量少于25个汉字；过长问题分句。
- 先说来源，再问一个最关键的问题。
- 一次只问一个用户可以立即回答的问题。
- 不朗读 JSON 字段名，例如把 `duration` 说成“时间”。
- 不朗读文件路径、异常类名、token、耗时和段落统计细节。
- 用户开始说话后立即停止或禁止启动 TTS。
- TTS 失败时保留 SCREEN 文本，不影响记录和会话。

## 8. 实施顺序

1. 定义 `UserNotice`/`PresentationMessage` 数据对象和消息类别。
2. 将 `display_completed_segments()` 改为产生数据，不直接输出用户对话。
3. 增加优先级队列，并按语音预算组成短消息组。
4. 分离用户模式与 debug 日志。
5. 真实验收输出顺序和实验步骤编号。
6. 上述稳定后，TTS 只消费 `VOICE` 类型消息。

本策略不要求本轮立即接 TTS。

## 9. 交互职责边界

下列职责从现在起固定，后续接终端、前端和 TTS 时均遵守同一边界：

| 职责 | 负责模块 | 不负责的内容 |
|---|---|---|
| 将 ASR 文本识别为结束、暂缓、查看、肯定、否定、指定问题等命令 | `InteractionCommandParser`（已实现） | 不修改问题状态，不打印，不播放语音 |
| 保存待确认问题及其 ACTIVE、DEFERRED、RESOLVED、EXPIRED 状态 | `PendingClarification` | 不决定界面颜色和播报时机 |
| 将用户答复匹配到具体问题并提交状态变化 | `ReplyCoordinator` | 不直接打印，不调用 TTS |
| 定义消息语义、优先级、渠道和朗读策略 | `PresentationMessage` | 不决定当前时刻能否播放 |
| 对消息排序、取消过期消息，并按认知负担预算组成消息组 | `PresentationCoordinator`（待新增） | 不识别用户命令，不直接访问麦克风 |
| 判断当前是否处于可播报安全间隔 | 会话控制器/状态机 | 不决定消息业务优先级 |
| 将消息呈现在终端或未来前端 | Screen Renderer（待抽离） | 不修改实验事件和待确认状态 |
| 播放允许朗读的消息并处理播放失败 | `TTSClient`/TTS Controller（后续） | 不自行挑选业务问题 |
| 保存原始口述、事件、确认答复和问题状态变化 | storage 层 | 不控制展示顺序 |
| 串联上述模块和处理资源生命周期 | `main.py` | 不长期保存命令词表和复杂业务判断 |

### 当前命令规则所在位置（2026-08-12）

- 结束实验、暂缓、查看、肯定、否定和指定问题的规范化与精确解析：`src/core/interaction_command.py`；
- 肯定答复保守匹配：`src/core/reply_coordinator.py`；
- 暂缓/回看处理：`src/core/clarification_command_handler.py`；指定编号答复：`src/core/targeted_clarification.py`；
- 新统一链动作执行：`src/core/clarification_executor.py`；旧 main 门卫仍待统一清理；
- 输出渠道和是否允许朗读：`src/core/presentation_message.py`；
- 当前终端输出顺序：仍主要位于 `src/main.py`，尚未迁移到展示协调器。

### 命令判断原则

所有用户原始 ASR 必须先保存，再判断命令。命令匹配采用上下文约束：

1. “结束实验记录”仅在整句匹配受支持命令时结束，不能把“结束离心后取样”误判为结束会话；
2. “是的”只有存在可匹配确认项时才作为确认答复；
3. “这个先跳过”只有存在当前正在询问的问题时才暂缓该问题；
4. “查看待确认问题”只产生回看请求，不改变问题状态；
5. “问题2，离心5分钟”先定位问题，再由协调器提交答复；
6. 匹配存在歧义时不猜测，要求用户说明目标。
