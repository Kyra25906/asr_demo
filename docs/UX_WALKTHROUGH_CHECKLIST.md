# 体验走查清单（UX Walkthrough Checklist）

首版：2026-08-14（用户提出"终端输出看不出用户体验如何"后建立）

> 本文档定义"体验验收"的固定检查表、标准走查脚本、记录模板和判定规则。
> **功能验收与体验验收是两个独立维度**：
> 功能验收（测试绿、REAL_OK）证明"系统行为符合规格"；
> 体验验收（UX 走查）证明"真实使用者能看懂、不困惑、节奏顺、不被打扰"。
> 二者不能互相替代：`REAL_OK` 不等于"体验好"。
>
> 与 `OUTPUT_PRESENTATION_POLICY.md` 的关系：该文档定义输出职责与政策
> （应该输出什么、什么渠道、什么顺序）；本文档定义如何验收输出
> （实际输出是否达到政策要求、体验是否可接受）。PRESENT 落地后，
> 用本文档第 8 节的基线逐项对比，证明体验改善而非只报"功能已集成"。

## 1. 为什么需要（背景与根因）

用户 2026-08-14 提出：每轮 agent 验收只聚焦"能力有没有实现"，忽略"用户体验如何"；
终端输出难以看出体验好坏，双方对"最终构建的东西怎么样"说不清楚。

根因：

1. **证据类型错配**：功能验收证据（测试数、JSONL 数、session_id、token 数）
   证明"功能正确发生了"，不证明"体验好"。
2. **体验是人的判断**：体验 = 真实使用者的主观感受 + 可观察行为，
   agent 无法替真实使用者裁决，只能收集证据。
3. **输出本身未分层**：`main.py` 42 处散落 `print()`，用户对话、识别结果、
   开发调试信息（`[统一链] 目标=权限=缺失字段=…`）、状态混在同一终端，
   实时看不过来（2026-08-14 基线会话中用户直接反馈"边口述边判断看不过来"）。

## 2. 适用范围（何时必须走查）

- **必须走查**：本轮改动改变了"用户能看到的输出或交互路径"——主流程输出、
  屏幕/TTS 消息、交互顺序、错误提示、前端渲染、唤醒/结束路径。
- **可不走查**：纯内部逻辑（无输出面变化）的轮次，功能验收即可，
  但须在交接文档说明"本轮无输出面变化"。

判断方法：问一句"用户运行程序时，屏幕上/耳朵里看到听到的内容，
跟上一轮比有没有变化？"——有变化就必走查。

## 3. 九维走查表

每维统一格式：**检查方式（操作 → 预期 → 失败标志）→ 证据来源**。
证据来源分三类：`代码静态`（读代码可判定）、`输出流`（看会话输出文件可判定）、
`用户裁决`（必须真实使用者表态）。

| # | 维度 | 检查方式 | 失败标志 | 证据来源 |
|---|------|---------|---------|---------|
| 1 | 信息分诊（Output Channeling） | 全程看屏幕：除对话/回执/状态/待确认列表外，是否出现 `目标=`、`权限=`、`缺失字段`、request_id、文件路径、异常堆栈等开发语言 | 出现上述任一调试语言 | 输出流 |
| 2 | 顺序正确（Turn-taking） | 用户上一句的回答，其回执必须先于任何新消息出现；追问不得早于回执 | 先出现新追问/新状态，后出现回执 | 输出流 |
| 3 | 问题唯一（One Question at a Time） | 每个安全间隙内，用户明确知道"当前要我回答的一个问题"；待确认列表只作参考，不要求立即回答 | 同时出现两个无主次的问题；或系统在等待回答但屏幕没有明确问题文本 | 输出流 + 用户裁决 |
| 4 | 编号一致（Numbering Consistency） | 屏幕上的实验步骤编号、问题编号与内部 utterance 编号分离；用户编号不跳号、不混淆 | 显示"第4段"而实验步骤只有3个；确认答复占用了步骤编号 | 输出流 |
| 5 | 反馈及时（Feedback Latency） | 每段口述后，"已记录/已确认/降级保存"等状态在进入下一轮监听前可见 | 口述后长时间无任何反馈，且无"处理中"说明 | 输出流 |
| 6 | 容错可见（Fail-soft Visibility） | 降级/保存失败/识别失败时，用户知道"发生了什么 + 数据是否已保存 + 下一步怎么做" | 只有异常类名/堆栈，无面向用户的人话说明 | 输出流 |
| 7 | 可理解性（Plain Language） | 屏幕与 TTS 文本无 JSON 字段名、token 数、模型名、文件路径、英文错误码 | 出现上述任一 | 输出流 |
| 8 | 语音预算（Voice Budget） | TTS 一次最多一个追问+一个回执；不朗读"已记录"；不打断用户说话（TTS 未接前此维记"不适用/待TTS轮"） | 朗读长段、打断用户（TTS 轮才可判定） | 用户裁决（TTS 轮） |
| 9 | 响应速度（Response Latency） | 从说完整句到屏幕出现反馈的耗时：识别完成到反馈的间隔，记录实测值；不出现"无响应且无提示" | 口述后超 2 秒无任何新内容且无"处理中"提示（LLM 处理期须有说明） | 输出流（时间戳） |

## 4. 标准走查脚本（固定路径）

场景：模拟评审/路演的连续会话。**执行原则：口述者只看脚本提示，不看屏幕；
屏幕输出由程序重定向到文件，判断在事后离线进行。**

```text
第 0 步  启动程序，输出重定向到 results/walkthrough_baseline_<日期>.txt
         （冷启动约 113 秒；看到"实验语音智能体已启动"后进入第 1 步）
第 1 步  唤醒："小科小科"        → 记录唤醒反馈（文字+提示音）
第 2 步  实验口述 1："先加入5毫升缓冲液"
第 3 步  实验口述 2（依赖1的内容）："加热到六十摄氏度"
第 4 步  若产生追问，回答（带编号）："问题一，是5毫升"
第 5 步  查看："查看待确认问题"
第 6 步  结束："结束实验记录"    → 记录结束汇总输出
第 7 步  会话结束后，逐项核对九维表，填写记录模板
```

每一步的记录内容：**屏幕原文（照抄）、时间点、口述者此刻是否知道下一步做什么**。
"口述者是否知道下一步"这一栏由口述者事后口头回答，agent 不得代填。

## 6. 判定规则与状态

状态定义（写进任务清单）：

| 状态 | 含义 |
|---|---|
| `UX_PENDING` | 本轮涉及输出面但尚未走查 |
| `UX_WALKED` | 走查完成，证据记录在本文档第 8 节 |
| `UX_CONFIRMED` | 用户实际体验后确认通过 |
| `UX_ISSUES` | 走查发现体验问题（登记任务清单：现象/复现路径/期望） |

流转：`UX_PENDING → UX_WALKED → UX_CONFIRMED 或 UX_ISSUES`

分工边界（必须遵守）：

- **agent 负责**：执行走查、逐行读输出文件、收集证据、判定可客观判定的维度
  （1/2/4/5/6/7/9 及 3 的输出流部分）。
- **用户负责**：最终裁决"是否顺、是否困惑"（3/8 的主观部分 + 整体结论）。
- **禁止**：agent 把"功能验收通过"写成"体验验收通过"；
  `UX_WALKED` 不能替代 `UX_CONFIRMED`。
